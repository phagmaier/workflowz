# Workflowz Workbench user guide

Workflowz runs the steps and Outcome rules you author, one step at a time. Use the
Workbench to inspect a workflow, save it, prepare a run and decide when execution starts.
An agent can do work inside a step; the workflow's connections decide what runs next.

This guide describes the current local service and browser interface. For installation
requirements and build commands, see [README.md](../README.md#development).

## Start and pair

After the setup in the README, start the local service from the repository root:

```bash
bin/wf --state-dir "$HOME/.local/state/workflowz" daemon start
```

Leave that terminal open. In another terminal, also from the repository root, run:

```bash
bin/wf --state-dir "$HOME/.local/state/workflowz" ui
```

Open the printed browser address, paste the one-use **Pairing code**, and choose
**Connect**. The interface is served at `/ui/`. Use the same state directory for every
command so you return to the same saved workflows and runs. An existing state directory
must belong to you and have private permissions (`0700`).

The code expires after five minutes, works once, and is replaced if you request another.
Run the `ui` command again if you need a fresh one. Treat it like a password. Browser
sessions last 12 hours and end when the service restarts or another browser pairs.

The sidebar shows the service connection. If it becomes unavailable, check the service
terminal. If the browser asks you to pair again, issue a new code. Closing, reloading or
disconnecting the browser leaves execution running in the service. Unsaved editor work
is different: **drafts and unsaved changes live only in the current tab and are lost on
reload or tab closure**. A draft address opened in another tab does not carry its content.

## Import or create a workflow

### Import your file

1. Open **Workflows**, or choose **Import file…** in the sidebar.
2. Drop a workflow YAML file into **Import a workflow file**, or use **Choose file…**.
   Files can be written by you or generated by an agent; the browser import limit is 1 MiB.
3. Paste the full **Workflow folder** path on the service's machine. This is the folder
   the file came from; the browser cannot infer it from the chosen file.
4. Choose **Open draft**.

A parsed import opens in **Graph**, including a workflow with broken routing that needs
repair. Malformed or schema-invalid YAML, or a failed import check, opens as editable text
in **YAML** so you can keep and repair the original text. Importing does not save or run it.

The workflow folder and project folder serve different purposes. A relative
`project.root` starts from the workflow folder. Instruction files, prompt files and the
task checklist are relative to the resulting project folder. For example, importing
[examples/command-only.yaml](../examples/command-only.yaml) with the repository's `examples`
directory as **Workflow folder** makes its `project.root: ".."` resolve to the repository.

Ask an agent generating a file to use Workflowz's version 1 format, declare each agent's
Outcomes and connect every normal Outcome. Give it the
[schema reference](reference/schema-v1.md) and the intended project path. Read the resulting
commands, prompts and routes before starting a run.

### Start from an example

Choose **New workflow**, enter a **Name** and an absolute **Project folder**, then select:

| Starting point | Initial workflow |
| --- | --- |
| Single agent step | One prompt, an agent and a finish step. |
| Task loop | Pick a task, implement it, mark it done and repeat. Supply a Markdown checklist path. |
| Commands only | A command initially set to `npm test`, followed by a finish step. |

Choose **Create draft**. New drafts normally open in **Form**, as do saved workflows
opened from Workflows or the sidebar. Nothing has been saved yet.

For a small first example, choose **Commands only**, name it “Node version”, and use an
existing project folder. Select **Run tests**, replace its **Command** with
`node --version`, and optionally rename the step to “Node version”. Leave `complete`
leading to **Done** and `failed` set to **Pause and wait for me**. This example uses no agent
or provider. Continue through the editing and run steps below. A
[complete YAML version](#reference-yaml-and-terminal-commands) is in the reference section.

## Inspect, edit and check

**Graph** and **Form** edit one shared draft. Switch between them whenever useful; an edit
in either appears in the other. **Project**, **Rules & limits** and **YAML** belong to that
same draft.

In **Graph**, select a step to open its settings. Select an Outcome on its node to choose
what happens after that result. **Tidy up**, **Fit** and the zoom controls help inspect
branches and loops. Layout is automatic; scroll inside a large graph if Fit makes labels
too small.

In **Form**, select a step in the table to configure it beside the table. Outcome buttons
take you to the matching destination field. On smaller screens, settings appear below
the steps; **Back to steps** returns you to the list. With a step's table button focused,
Alt + Up/Down changes its display order.

**Runs first** chooses the first step. After that, **Outcome destinations determine
execution order**. Graph placement, Tidy up and the table's display order do not choose
what runs next. A connection back to an earlier step creates a loop, regardless of where
the node is drawn.

Use **Add step** to create a step, then configure it and connect it. Adding a step alone
does not put it on an execution path. A destination selector also offers **New step…**
to create and connect a destination together. You can rename or delete selected steps;
deleting a destination leaves visible problems for you to repair.

For a **Command**, enter a program and its arguments on one line, such as
`node --version`. Quotes group arguments; backslashes escape characters. Unfinished
quotes or escapes stay in the draft and block saving. The editor does not add a shell:
operators such as `|`, `&&` and `>` require an explicit shell command. See the
[YAML and terminal reference](#reference-yaml-and-terminal-commands) for an example.

For an **Agent**, choose the harness, model if needed, prompt and declared **Outcomes**.
Each Outcome needs a destination, a pause or a retry rule. The agent must report one of
those names. Advanced step settings contain working-folder overrides, time limits,
instruction files, report context, command environment variables and tags as applicable.

In **Project**, verify the project folder, instruction files and optional task checklist.
Paste paths in the browser; there is no project-folder chooser yet. Instruction files
listed here are given to every agent, in the listed order.

### Use the checker

The bottom **Checker** is available across editor views. Changes are checked against the
service. Read each problem and choose **Fix →** to open and focus the relevant field;
Fix navigates to the repair, rather than inventing a change. Step and Outcome fixes keep
you in Graph or Form when possible. Project, rules, limits and YAML problems open their
corresponding views, including Advanced fields when needed.

For example, after adding an agent Outcome such as `needs_info`, use its checker Fix
action and choose **Pause and wait for me** or a destination step. Wait for the newest
check to finish before saving. Errors block Save and run creation; warnings need review
but can allow them. “All good” means the workflow passed the checks, not that its commands
or agent work have been executed successfully.

If a check fails to load, your edits remain in the tab. Choose **Check again**. Old
diagnostics may stay visible, but their Fix actions and saving remain unavailable until
the latest draft has been checked.

## Save, create a run and start

These actions have separate effects:

| Action | What it does |
| --- | --- |
| Save | Stores an immutable, numbered workflow revision. Creates no run. |
| Create run | Prepares a run with its revision and imported tasks. Executes nothing. |
| Start run | Begins executing the prepared run. |

1. Choose **Save** after reviewing the draft and checker. Confirm the saved revision number
   beside the workflow name. Later edits and saves produce another revision; they do not
   rewrite previous revisions or existing runs. Workflows lists the latest saved revision
   for each name and lets you expand its **earlier revisions**.
2. Choose **Create run…**. Review the preparation panel. If there is a task checklist,
   inspect the tasks that will be copied and **All checklist items**; checked items are
   excluded unless you explicitly include them. Choose **Create run** in that panel.
3. The new run opens **Ready to start**. Review **What will run**, its first step and Outcome
   destinations, the imported tasks and the project folder in **Run information**. **Map**
   also shows the run's workflow. Merely opening this page executes nothing.
4. Read the permissions note, then choose **Start run** when ready. Agents run with
   unrestricted permissions; commands run as your user. Both can change files you can
   access, including outside the project. **Stopping does not undo changes.**

You can also create a run directly from a checked draft with unsaved changes. The panel
states that it will keep those changes as a revision with the run. Saving first makes
the revision you intend to use explicit.

For the Node version example, the command runs, `complete` leads to Done, and the run
finishes. Select its command in History to read the saved version output.

If Save or Create run gets no answer from the service, the result may be unknown. Check
**Workflows** or **Runs** before trying again. Controls do not automatically resend changes.

## Find runs and inspect results

Open **Runs** for all groups, or use a sidebar status link to jump to a group. All four
groups remain visible, with newest runs first within each group:

| Group | Statuses |
| --- | --- |
| Waiting for you | Paused; interrupted and awaiting recovery. |
| Ready to start | Draft or ready runs that have not started. |
| Running | Running; pausing while the current step finishes. |
| Finished | Completed or stopped. |

Use the workflow name or **Open** on a run to inspect it. Check the run ID and revision
when several runs share a name. Opening does not start or resume execution. A failed
refresh can leave the last known rows and counts visible with an out-of-date notice;
use the retry action before relying on that state.

Run details shows the current status, next or current step, task progress and elapsed
time. Elapsed time includes pauses. **Refresh run** updates the view. **Open workflow**
opens the saved revision in the regular editor; use the paused-run change action below
to change the workflow of an existing run.

### History, Report and Output

**History** groups steps and run events, including task groups when applicable. Select
an attempt to see its result, timing and what happened next. Initially the view follows
the latest step; selecting or interacting with attempt details keeps that selection
while background work progresses. Select another entry to inspect newer work. On a
narrow screen, **View selected step** moves focus to the details below.

Each attempt offers **Report** and **Output**:

- Commands normally open on **Output**. Agents normally open on **Report**. Your tab
  choice is remembered for each attempt during this page load, including visits to Map.
- **Report** shows the recorded result and, for an accepted agent report, its summary,
  issue or handoff when supplied. It also explains manual results, failures and routing.
  **Accepted report**, **Step definition** and **Technical details** provide more evidence.
- **Output** shows bounded saved capture from the latest settled invocation, up to
  64 KiB of standard output plus an available diagnostic excerpt of error output.
  It does **not stream live output**. While a step runs, capture may be unavailable until
  settlement. Empty output, unavailable capture and a failed read have different messages;
  use **Refresh output** or **Try loading output again** as appropriate.
- Read truncation notices outside the output scrollers. The view may show only the first
  64 KiB, the underlying capture may have reached its own limit, and error diagnostics may
  be shorter than the full error stream. Displayed text is not a complete terminal log.
  Earlier invocation evidence, including a report-correction attempt, stays in Technical
  details; a clean correction need not show an earlier invocation's stderr in Output.

Historical attempts retain the definitions from **their original revisions**. After a
workflow change, the “Definition from revision …” line can differ from the run's current
revision. Earlier prompts, commands and reports remain historical records.

### Map and Run information

**Map** is a read-only view of the current revision and the execution path. Select a step
to inspect it and use **Show latest result in history** when offered to return to its
latest recorded result. Changing the map selection does not change execution.

Expand **Run information** for the project folder, creation details, imported task bodies
and **Attention records**. Attention notices remain as history after a decision; use the
current run status to tell whether action is still required.

## Pause, decide, change or stop

### Pause and choose what happens next

While running, **Pause after this step** lets the current step finish and settle before
pausing. **Pausing** means the service is still waiting for that settlement. A workflow
Outcome can also pause the run for you.

A paused run offers choices under **What should happen next?**. Available choices depend
on its current step and task state. Every manual decision needs a reason, saved in History.

| Choice | How to use it |
| --- | --- |
| Run this step again / Continue with … | Give a reason, then choose **Resume run**. Rerunning starts the step from the beginning and can repeat effects already made. |
| Decide …'s result yourself | Choose a declared result and give a reason, then **Apply**. Records a manual result and follows its rule while keeping the run paused; it does not create an agent report. A retry destination remains paused instead of retrying automatically. |
| Continue from another step | Choose a compatible step and give a reason, then **Apply**. Moves the next step without changing task progress. |
| Mark this task done | Choose the task and give a reason, then **Apply**. Marks it done without running remaining steps. If it was current, you may need to move to the step that picks the next task. |

**Apply leaves the run paused.** After a manual result, step change or task completion,
the interface selects the continuation choice and carries your reason forward. Review
the next step and reason, then explicitly choose **Resume run** to execute. Nothing
reruns just because you applied a choice.

If the run changed elsewhere, a stale action is refused. Read the refreshed state and
choose again. Failed requests keep your input and do not resend themselves. If an action's
result is unknown because the service did not answer, inspect the run before repeating it.

### Change the workflow of a paused run

1. Select **Change the workflow for this run**, then **Edit the workflow for this run**.
2. Edit using the same Graph, Form, Project, Rules & limits and YAML views. Review the
   displayed changes and checker. The project folder and imported task source stay fixed.
3. Review **Continue at**. Keep the current step if compatible, or choose another. Steps
   that need an active task are unavailable without one; a next-task step cannot pick
   another task while one is still active. The interface explains unavailable choices.
4. Enter a reason and choose **Apply to this run**. It creates a revision for this run's
   remaining work, preserves previous history and leaves the run paused. Saved workflows
   and other runs do not change. Applying itself does not execute commands or modify
   project files. Agent conversations from the previous revision cannot be resumed.
5. Back on the run, review its next step and choose **Resume run** with a reason when ready.

If the run moved while you edited, use **Check the run again**. Your edits are kept in
the tab. If another operator changed the workflow revision, the editor asks you to
discard your changes to start from that current workflow.

### Stop or cancel

Use **Stop run now…** while running or pausing, **Stop this run…** while paused, or
**Cancel this run…** before Start. Enter a reason and confirm **Stop run**. For active
work, the service ends the owned process and waits for cleanup. File changes remain.
**A stopped run cannot be resumed**; prepare a new run if you want to execute again.

Closing the browser is not a stop action. To shut down the service itself, run this in
another terminal using the same state directory:

```bash
bin/wf --state-dir "$HOME/.local/state/workflowz" daemon stop
```

Service shutdown waits for current work to settle and pauses active runs; it may take
time. Use the run's Stop control first if you intend to terminate its current operation.

## Recover an interrupted run

An unexpected service exit during execution can leave a run **Interrupted**. Restart
the service with the same state directory, pair again and open the run under **Waiting
for you**. The page shows the step, attempt and known process state, with the heading
**Recovery happens in the terminal for now**. There is no browser recovery wizard.

Workflowz never automatically replays uncertain work or recovery signals. A process
being gone does not tell you what it changed. Inspect the project and any external
effects before deciding whether rerunning is appropriate.

The commands below run from the repository root. Replace `RUN_ID` with the displayed
run ID and `EVENT_ID` with the latest event number from the indicated inspection.

1. Inspect durable recovery evidence and the currently available `actions`:

   ```bash
   bin/wf --state-dir "$HOME/.local/state/workflowz" run recovery RUN_ID
   ```

2. If you need a fresh observation of the process, use **run status** to get
   `expectedEventId`, then reconcile and inspect recovery again:

   ```bash
   bin/wf --state-dir "$HOME/.local/state/workflowz" run status RUN_ID
   bin/wf --state-dir "$HOME/.local/state/workflowz" run reconcile RUN_ID --expected-event EVENT_ID
   bin/wf --state-dir "$HOME/.local/state/workflowz" run recovery RUN_ID
   ```

   Reconcile observes state; it does not signal or rerun the operation.

3. Resolve any process barrier first. Follow the offered actions, rather than assuming
   an absent or unrecognized process is safe to replay. Recovery request files contain
   `expectedEventId`, `attemptId` and a nonblank `reason`, for example:

   ```json
   {
     "expectedEventId": 42,
     "attemptId": "attempt_REPLACE_WITH_INSPECTED_ID",
     "reason": "Reviewed the interrupted operation and its effects"
   }
   ```

   These are illustrative values: replace the event number and attempt ID with the
   **latest recovery response** before submitting each request. Use JSON `null` for
   `attemptId` when the response has no attempt.

   If `terminate` is offered, save that request as `recovery-request.json` and explicitly
   ask the service to terminate its verified owned process group:

   ```bash
   bin/wf --state-dir "$HOME/.local/state/workflowz" run recovery-terminate RUN_ID --request recovery-request.json
   ```

   If `confirm_external_cleanup` is offered, first establish outside Workflowz that no
   operation survives. Add `"confirmedNoSurvivingOperation": true` to the request and
   record that confirmation with:

   ```bash
   bin/wf --state-dir "$HOME/.local/state/workflowz" run recovery-confirm RUN_ID --request recovery-request.json
   ```

   Confirmation cannot bypass a verified live owned process. Reinspect recovery after
   each action; another unresolved attempt may still need attention. Unresolved work
   can block execution of other runs in the same state directory.

4. Once `processResolved` is true and the decision is offered, prepare `decision.json`
   with fresh `expectedEventId`, `attemptId`, a reason and an `action`. For example, only
   after deciding it is appropriate to repeat the interrupted step:

   ```json
   {
     "expectedEventId": 47,
     "attemptId": "attempt_REPLACE_WITH_INSPECTED_ID",
     "reason": "Reviewed effects; deliberately run the interrupted step again",
     "action": "retry"
   }
   ```

   | Decision | Effect |
   | --- | --- |
   | `retry` | Selects the interrupted step to run again from the beginning. |
   | `continue` | Continues the committed cursor when interruption occurred between steps, with no interrupted attempt; use `attemptId: null`. |
   | `skip` | Adds an `outcome` field containing a declared result for the current step and applies that result manually. |
   | `jump` | Adds a `stepId` field naming a compatible continuation step. |
   | `end` | Stops the run. |

   Submit the decision:

   ```bash
   bin/wf --state-dir "$HOME/.local/state/workflowz" run recovery-decide RUN_ID --request decision.json
   ```

5. A non-ending decision leaves the run **Paused**. Inspect it in the browser and
   explicitly choose **Resume run**, or obtain the new event number and resume in the
   terminal:

   ```bash
   bin/wf --state-dir "$HOME/.local/state/workflowz" run status RUN_ID
   bin/wf --state-dir "$HOME/.local/state/workflowz" run resume RUN_ID --expected-event EVENT_ID --reason "Continue after reviewed recovery"
   ```

Requests are bound to the inspected event and attempt. If refused as stale, inspect
again and make a fresh decision; never blindly resubmit an old request. For more detail,
see the [runtime recovery contract](reference/architecture.md).

## Reference: task loops

Use a Markdown checklist under **Project → Task checklist**, or choose the **Task loop**
example. Its basic path is:

```text
Pick task → Implement → Mark done → Pick task
    └─ no tasks left → Done
```

The **Pick the next task** step (`task.next`) takes the next queued task. Its `task_ready`
Outcome leads to work; `exhausted` leads to a finish step. **Mark task done**
(`task.complete`) marks the active task done in Workflowz, then normally returns to
Pick the next task. These are workflow steps, not commands or agents.

Tasks are copied when the run is created, in checklist order. Checked items are excluded
unless you include them in the creation preview. Later file edits do not change the run,
and Workflowz never ticks boxes in the source checklist. Task bodies are available under
Run information. Prompts can use `{{task.text}}` for the active task.

A checklist alone does not create iteration; the steps and Outcome connections do.
The example's step-execution limit also counts task-control steps and returns around the
loop. Task-specific overrides, when needed, are available through the CLI and described
in the [schema reference](reference/schema-v1.md).

## Reference: shared rules and retries

Use **Rules & limits → Shared rules** to apply a result rule to named steps, steps
matching any of a set of tags, or all steps. Add tags in a step's **Advanced** settings.
**Workflow defaults** apply when no more specific rule chooses the destination.

For any result, priority is: step rule → named-step shared rule → tag shared rule →
all-step shared rule → workflow default. Exact technical-failure rules are considered
before the “any technical failure” fallback, across all those levels. Conflicting
rules at the same level need repair. Inherited destinations show their source after a
current check; “check needed” means the editor cannot yet resolve them.

An Outcome destination can go to a step, finish through an end step, **Pause and wait
for me**, or retry the same step. Retry settings specify **Runs in total (2–100)**,
including the first run, and **Wait between runs (seconds)**. Exhausting that retry
budget pauses for you. Retrying can repeat effects; it does not restore files. Engine
task-control steps do not support invocation retries. The Graph draws normal Outcomes;
technical-failure rules are inspected in settings and Rules & limits.

## Reference: technical failures and reports

A command exit code of zero produces `complete`; a nonzero exit produces `failed`.
An agent instead submits a structured report containing one of its declared Outcomes.
Those are normal workflow results. Failure to start a process, a timeout, a process
failure or a missing/invalid agent report is a separate technical failure.

Expand **If something goes wrong technically** in step settings to inspect or override
technical failure routes. Specific failures such as `system.timeout` take priority over
`system.error`, the “any technical failure” fallback. Unrouted technical failures pause.
These reserved `system.*` names are not Outcomes an agent may declare or choose.

**Rules & limits → Workflow defaults → Ask the agent once for its report** controls
one possible correction after a clean invocation without a valid report. It asks in
the exact same session only when supported by the harness. It does not repair the
original technical execution failure, and never accepts an undeclared result. Review
Report, Output and Technical details before deciding how to continue a paused failure.

## Reference: limits

Use **Rules & limits → Safety limits**. Empty fields mean no limit.

| Limit | Meaning |
| --- | --- |
| Maximum step executions | Counts committed transitions, including retries and task-control steps. Reaching it pauses the run. |
| Maximum run time (seconds) | Wall time since Start, including pauses and service downtime. Caps active commands/agents at the remaining time, then pauses the run without starting further steps. |
| Agent silence timeout (seconds) | Ends an agent invocation after that long without stdout or stderr. Routes as a technical timeout; commands are unaffected. |
| Step Advanced → Time limit (seconds) | Limits an individual agent or command invocation. |

Limits do not undo changes or isolate work. The checker warns about loops without a
step-count or wall-time limit. If an exhausted run limit prevents continuation, change
the limit through the paused-run workflow editor before explicitly resuming.

## Reference: agents and effort preferences

Agent steps use separately installed harnesses: Codex, Claude Code, OpenCode, Pi or
oh-my-pi (OMP). Configure and authenticate the chosen harness outside Workflowz. Check
the selected model and permissions before starting; the example agent defaults are
starting points you should review.

**Reasoning effort** is a step setting. Empty uses the harness's own default. OpenCode
values are variants supported by the chosen provider/model; a suggestion is not a promise
that every model supports it.

Open **Effort defaults** beneath that field to set a preference per harness in this
browser. New agent steps and new workflow examples use these preferences. Existing
and imported steps keep their own values until you change them or choose **Use my …
default**. Recent custom values are offered again. The chosen step value is saved in
the workflow; defaults and recent-value history are separate browser settings. If
browser storage is unavailable, preferences last only for the current tab.

**Conversation** chooses a new conversation or continuation of a previous conversation
for the task. Continuation requires a supported matching session; it cannot silently
fall back to a fresh conversation. A run's workflow revision change ends eligibility
to resume sessions from its old revision.

## Reference: YAML and terminal commands

**YAML** shows the exact text Save or Apply will send. Choose **Edit as text** to keep
comments, formatting and unfinished edits. Visual editing pauses while text is the
source of truth. After the text passes validation, choose **Return to visual editor**,
then Graph or Form. Subsequent visual edits regenerate YAML and remove comments.
Visiting Graph or Form alone does not rewrite an untouched import. Save stores a
revision in Workflowz; it does not overwrite the original imported file.

Here is a complete, command-only workflow for the Node version example. Save it as
`node-version.yaml` in an existing folder; import with that folder as Workflow folder.
Its `project.root: .` uses the same folder:

```yaml
version: 1
name: Node version
project:
  root: .
start: node_version
steps:
  node_version:
    kind: command
    argv: [node, --version]
    on:
      complete: { goto: done }
      failed: { pause: true }
  done:
    kind: end
```

Validate a file without starting a service or executing its steps:

```bash
bin/wf workflow validate node-version.yaml
bin/wf workflow validate examples/command-only.yaml
```

The command field represents an argument array, not a shell script. For an intentional
pipeline, enter an explicit shell invocation such as:

```text
sh -c 'printf "hello\n" | wc -l'
```

For existing YAML, argument arrays preserve empty arguments and embedded newlines.
Step IDs and Outcome names use lowercase letters, digits and underscores, starting
with a letter. Use the [version 1 schema reference](reference/schema-v1.md) for the full
format, placeholders and task overrides, and [examples/](../examples/README.md) for more
workflows. Example agents, models and commands need review for your environment.

`bin/wf --help` lists the CLI controls. Workflow validation is local; importing, run
management and browser pairing use the service. CLI controls use the same saved state
and stale-state checks as the browser. For terminal recovery and management, always
pass the same `--state-dir` used to start it.

## Current limitations

Known usability gripes and proposed improvements are tracked in
[IMPROVEMENTS.md](../IMPROVEMENTS.md). This guide describes the implemented behavior;
an open suggestion there is not yet a feature.

This release is the browser-served Workbench. Desktop packaging, automatic service
lifecycle, the operating-system project-folder picker, notifications and desktop
quit/reopen behavior remain future work. System fonts are used; bundled fonts and
associated CSP changes remain undecided. Graph placement is automatic, output is saved
bounded capture, and interrupted recovery requires the terminal as described above.

Interface regression checks use offline Chromium and fake adapters. Completed real-provider
[evaluations](README.md#evaluations) and their limitations are recorded separately. The guides
under [history/](history/README.md) describe superseded interfaces.
