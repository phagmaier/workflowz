# Workflow schema v1 — implementation decisions

This file records how the implementation resolves points that `spec.md` §3 leaves open, and where it differs from the spec's field names. Any change here must also be reflected in `spec.md` or `architecture.md` (AGENTS.md change protocol).

The reference fixture is [`examples/overnight.yaml`](../examples/overnight.yaml). It compiles with zero diagnostics. Negative fixtures live in [`test/fixtures/workflows/invalid/`](../test/fixtures/workflows/invalid/) and each is pinned to one expected code in `src/engine/compile.test.ts`.

## Accepted fields

| Level | Fields |
| --- | --- |
| top | `version` (must be `1`), `name`, `project` (`root`, `instructions`), `tasks` (`source.kind: markdown_checklist`, `source.path`), `start`, `limits`, `defaults` (`on`, `report_correction_attempts`), `policies`, `steps` |
| `agent` | `harness`, `model`, `reasoning_effort`, `session` (`fresh`\|`resume`, required), exactly one of `prompt`\|`prompt_file`, `instructions`, `cwd`, `outcomes` (required), `on`, `tags`, `timeout_seconds`, `context.include_reports` |
| `command` | `argv` (required, `argv[0]` non-empty), `cwd`, `env`, `timeout_seconds`, `on`, `tags` |
| `task.next`, `task.complete` | `on`, `tags` |
| `end` | `label` |
| `limits` | `max_wall_time_seconds`, `max_step_executions`, `agent_idle_timeout_seconds` |

## Decisions and deviations

1. **`timeout_seconds` instead of `timeout`.** Matches `limits.max_wall_time_seconds`, so every duration says its unit. Field name change only.
2. **`session` is required on agent steps.** The spec lists it without a default. An implicit `fresh` would hide a choice that changes which context the agent sees.
3. **`instructions` on an agent step is a list of paths, added after `project.instructions`.** The spec names the field but not its semantics. Paths resolve against the project root and must exist (checked by `checkReferencedPaths`).
4. **`limits.agent_idle_timeout_seconds` is accepted but not yet enforced.** It is validated now so workflows can state it. Enforcement belongs to the runner (todo Phase 3).
5. **`retry.max_attempts` counts total executions, including the first.** The spec example `max_attempts: 2` is read as "run the step at most twice". `max_attempts` must be at least 2, because 1 would be a no-op. The user confirmed this reading. `backoff_seconds` is validated and stored, but the runner does not wait yet (todo 7.4). A retry on an engine-only step (`task.next`, `task.complete`) pauses the run instead of rerunning it.
6. **`command` steps have fixed outcomes:** `complete` and `failed` (spec §3.2). Spawn errors route as `system.*`. `task.next` produces `task_ready` and `exhausted`. `task.complete` produces `complete`.
7. **Every normal outcome needs an exact rule.** That means a step `on` entry, a matching policy, or `defaults.on`. A missing one is an `incomplete_transition` error, not an implicit pause (spec §3.3, architecture §3).
8. **Policy selectors are exactly one of** `{tags: [...]}`, `{step_ids: [...]}`, or `{all: true}`. A policy whose tags match no step is a warning.
9. **Conflicts are checked per precedence level.** Two policies at the same level that cover the same step and outcome must agree. Policies at different levels never conflict, because precedence decides. The result does not depend on the order policies are written in (tested).
10. **`system.*` routing.** An exact rule wins. Otherwise `system.error` is tried through the same levels. Otherwise the built-in pause applies. Unknown `system.*` names are rejected at compile time.
11. **Harness validation has two stages.** The pure compiler checks registry capabilities for existing `session`, `model` and `reasoning_effort` fields. Each selected adapter exposes installed/implemented capabilities from its offline factory. Service preparation checks those capabilities on each effective attempt; unsupported model/reasoning selection routes `system.spawn_error`, unsupported explicit resume routes `system.resume_unavailable`, before provider execution. Registry conformance status describes implementation evidence; adapters remain explicitly supplied to the service. Optional correction support does not make resume a requirement for fresh work. Exact session availability is independently checked by adapters, not proven by help markers.
12. **Permissions default to each harness's unrestricted mode; there is no schema field.** The user chose this: adapters launch with the harness's yolo or full-access setting (table in [`harness-compatibility.md`](harness-compatibility.md#unrestricted-mode-used-by-the-adapters)). Each adapter must record the mode it launched with in the attempt's events, as spec §2.4 requires. The runner imposes no approval gates (spec §6).
13. **Placeholders are allowed only where they make sense.** The templated fields are `prompt`, `prompt_file`, `cwd`, `instructions` items, command `argv` items, and command `env` values. Placeholders in `name`, `project.root`, `tasks.source.path`, `label`, `harness`, `model`, and `reasoning_effort` are rejected.
14. **Triple braces (`{{{`, `}}}`) are rejected** as ambiguous.
15. **YAML aliases (`*name`) are rejected.** Anchors are accepted but unused. YAML 1.2 is used, so an unquoted `on:` key stays a string.
    Parsing always uses the core schema, including documents with legacy version directives. Unsupported tags and other YAML warnings are errors. Entries silently discarded by schema validation (for example, a `__proto__` record key) are rejected rather than lost.
16. **Loops.** A loop reachable from `start` produces an `unbounded_cycle` warning unless `limits.max_step_executions` or `limits.max_wall_time_seconds` is set. Analysis includes effective system-error routes; terminal `end` steps have no outgoing edges. Retries are not counted as loops, because their `max_attempts` bounds them.
17. **Missing files and directories** (project root, task source, instruction files, `prompt_file`, literal `cwd`) are checked by the caller with a supplied stat function, not by the compiler. The project root must be a directory. Values that contain placeholders are skipped.

## Identifiers

Step IDs, outcome names, and tags match `^[a-z][a-z0-9_]{0,63}$`. Dots are excluded so that placeholders and `system.*` names cannot collide with user names.

## Runtime decisions (phase 3)

These cover how workflow values are resolved and processes are run. They don't change the file format.

18. **Placeholders resolve at run time from fixed values.** `{{task.id}}` is the task's internal run-local ID. `{{task.text}}` is its title. `{{task.index}}` is 1-based in source order. `{{project.root}}` and `{{run.cwd}}` are both the project root, because runs have no separate working directory yet. `{{run.id}}` is the run ID. `{{steps.<id>.stdout}}` is the head of the latest run of that command step whose outcome was `complete`, capped at 64 KiB. `{{reports.<id>.*}}` reads the latest accepted report for that step within the current run and task. A missing explicitly referenced field pauses with `system.internal_error` before any process starts.
19. **A placeholder with no value is a pre-execution error.** The attempt settles as `system.internal_error` and no process starts, so a broken argument can never run half a command.
20. **Command environment is an allowlist plus `env`.** Children get `PATH`, `HOME`, `LANG`, `LC_ALL`, `TERM`, `TMPDIR`, `USER`, `LOGNAME`, and the XDG base directories, plus the workflow's `env` entries. Nothing else is inherited. A step that needs another variable must name it in `env`, and the value is stored in the workflow file. Keep secrets out of workflow files.
21. **Command `cwd` defaults to the project root.** A relative `cwd` resolves against the project root. A missing directory is a `system.spawn_error`.
22. **Reports use the private HTTP endpoint and real `wf report` CLI.** Stdout has no report authority, including in the fake fixture. The first valid report is committed with its event without moving the cursor. Only clean process settlement can consume it. A clean missing report permits one configured same-session correction; failed/unavailable correction routes `system.report_error`.
23. **Pause-after-current, stop, and resume.** A pause request while an attempt runs sets `pausing`. Settlement atomically records the outcome, routed cursor, and requested pause. A stop terminates the requested run's owned process group, waits until it has been reaped, and then records the stop. Stopping another saved run cannot affect the live operation. An unowned active attempt requires reconciliation first. The stopped attempt routes nothing. Resume starts the cursor step again from the beginning, so the user chooses the next step explicitly.
24. **Startup reconciliation never replays.** An attempt still active after a restart is marked interrupted and the run is marked interrupted, with a blocking item. Resuming runs the cursor step again only on explicit user action. Process-identity checks come with todo 7.1.
25. **Manual overrides are audited and need a reason.** `jump`, `skip` (take a declared outcome without running the step), and `mark_task_complete` apply only to a paused or interrupted run. Each one writes a `manual_override` event with the reason. A skip records its transition with no attempt, so it can be told apart from a real result.
26. **Unavailable sessions and adapter failures cannot silently succeed.** `session: resume` uses the most recent persisted session of the same harness, task, run and workflow revision. If absent it routes `system.resume_unavailable` before launch; it never falls back to fresh. A terminated agent produces `system.process_error` even if it exits zero with a declared report. Launch exceptions route `system.spawn_error`; a rejected completion promise requires process termination before `system.internal_error` can route. Unconfirmed cleanup leaves the attempt active rather than dispatching another process.

## Reporting decisions (phase 4)

27. **Report v1 is an out-of-band contract version.** The body is exactly `{outcome, summary, issue?, handoff?, data?}`; unknown fields (including authoritative IDs and transitions) are rejected. No extra model-authored version or control fields were added. Summary is nonblank; issue may be null; handoff is text; data is a JSON object. Bounds in UTF-8 bytes: summary/issue 4096 each, handoff 65536, serialized data 32768, HTTP body 131072. JSON is limited to depth 16 and 4096 nodes. The CLI reads bounded handoff content rather than persisting its path.
28. **Invocation tokens are opaque, memory-only, attempt-scoped and rotated for correction.** They authorize no run controls and expire on invocation settlement, stop, or channel shutdown. A body arriving after revocation is rejected even if its headers arrived earlier. Late/invalid authorization is 410, duplicate accepted report 409, invalid body/outcome 422, oversized body 413, durable acceptance 201. Tokens appear only in child environment and Authorization headers. The shared process supervisor scrubs injected secrets across stdout/stderr chunk boundaries; known report authorization is rejected in report content.
29. **One logical attempt includes at most two sequential invocations.** The original must settle before correction. SQLite persists the session identity and correction counter; the counter/event commit before invoking correction. Original and correction process IDs, settle details and distinct log paths are recorded as invocation events. Correction has a hard maximum of 30 seconds, can be configured lower on RunService, explicitly prohibits source modifications, and requires the exact same persisted session. An unsuccessful correction (including process/provider failure or timeout in that follow-up) routes `system.report_error`, preserving any report for diagnosis. Original failures retain their technical system outcome and bypass correction entirely.

## Task import and context decisions (phase 5.1–5.4)

30. **Import is read-only and immutable.** `RunService.previewTasks` exposes total/prechecked/runnable counts and source metadata. `createRun` reads the file again and atomically persists that actual source text/hash, include-completed choice, selected tasks and import event. It does not use a potentially stale preview as authority. Prechecked items are excluded by default; explicit `includeCompleted: true` queues them as pending while retaining their original checked state. Later file edits do not change the queue. Run-local IDs use original source order, including gaps from excluded items. Original line/column, indent, body and enclosing headings are durable. Automatic re-import remains unimplemented.
31. **The checklist parser handles ordinary local checklist documents.** Hyphen/asterisk checkboxes, lowercase/uppercase checked marks, nested items, CRLF, tabs, ATX/setext headings and fenced/standalone indented code are covered offline. Each checkbox is a separate task, never an implicit dependency. Continuation text preserves original indentation. It is not a complete CommonMark renderer: blockquote/HTML-contained checklist syntax and sophisticated embedded block constructs are outside this initial parser.
32. **Context is explicit and task-local.** Global instructions precede step instructions, read verbatim at attempt preparation. The task includes title, continuation body and heading ancestry. `context.include_reports` adds only the latest accepted report per named step within the current run/task; a selected step with no report yet is omitted (needed on the first pass of loops). An explicit report placeholder with no field value is an error. Unselected history is not added. The assembled input, including exact instruction content, is saved once per attempt before launch, excluding report authorization. Subsequent attempts read current instruction content; prior snapshots remain immutable. Correction uses its bounded report-only prompt and the persisted session, without reattaching instruction context.


## Run-local configuration decisions (phase 5.5)

33. **Task overrides are a separate strict API contract.** `RunService.setTaskOverrides(runId, taskId, {overrides: {steps: {...}}, reason})` replaces one unfinished task's complete settings; `{steps: {}}` clears them. Keys name existing agent/command step IDs. Allowed values are `{model?, prompt?, skip?: {outcome}, on?}`; model/prompt require an agent. Inline prompt replacement supersedes either original prompt form, and clearing restores it. The regular compiler checks placeholders, capability requirements, declared/known transition outcomes and existing targets. Selected `on` entries merge above step rules; unspecified entries retain ordinary policy/default resolution. No task IDs are added to YAML; no harness/session/outcome/step-kind changes, new nodes, per-task task-control edits or unrestricted graph patches are accepted. Unknown fields and silently discarded record keys are errors.
34. **Skip means an explicit per-task step outcome.** `skip: {outcome: complete}` skips that task's named executable stage via a declared normal outcome. It creates no attempt or accepted report, emits `step_skipped`, and commits a null-attempt transition. Task completion still requires `task.complete` or the existing manual completion operation. Taking a blocking outcome leaves the task active. Retry on a skipped stage pauses as for engine primitives; skip cycles consume the existing consecutive engine-step bound. Whole-task progress is never inferred from skipping an agent.
35. **Edits require ready/paused state, no active attempt, and a reason.** Task IDs must belong to the run and be unfinished. Edits during running, pausing, interrupted, completed or stopped states are rejected. Interrupted work must first receive an explicit recovery decision through existing controls. Migration 6 appends current task settings and immutable dispatch-time attempt parameters; prior migrations are untouched. State writes and `task_overrides_changed` / `workflow_revised` audit events share transactions, including rollback-only behavior after caught nested failures. Task settings changes retain old values in events; dispatched attempts retain their own settings regardless of later edits.
36. **Revision is validated replacement YAML for future execution.** `RunService.reviseWorkflow(runId, {workflowText, cursorStepId?, reason})` uses the original workflow directory, preserves normalized project root/task source, and validates all unfinished task settings against the replacement. Completed task settings remain historical. It updates the run's current revision/cursor only; task IDs/progress/source, active task, counters, prior definitions, attempts, transitions, reports and inputs remain intact. Repeated loop stages can use revised definitions on subsequent occurrences. Removed/kind-changed cursors require an explicit existing target. Task-next/task-complete and visible task placeholders must be compatible with active-task state even with an explicit cursor. Values inside files remain preparation-time checks; revisions do not read project files or re-import Markdown.
37. **Session scope is unchanged and explicit.** Model/prompt/transition edits preserve same-harness/run/task/revision session lookup. Definition revisions never inherit another revision ID's sessions; a resume stage without a matching identity produces `system.resume_unavailable` before launch, with no fresh fallback/correction. Identical YAML and source directory reuse the existing revision ID under the original content deduplication rule. Each attempt's frozen parameters plus revision reconstruct its effective definition; agent input additionally records harness, model and reasoning effort. Historical input snapshots are not rewritten.


## Codex adapter decisions (phase 6.1)

38. **Codex uses the existing report contract and session scope.** `createCodexAdapter` performs offline launch/resume flag probes before returning an adapter. Prompts use stdin; only explicit persisted session UUIDs may resume. JSONL supplies bounded session/terminal/failure evidence, never outcomes or transitions. A terminal event alone cannot settle the process. Model/reasoning effort pass through existing fields; no YAML fields or migrations were added. Invocation events now optionally include CLI version and permission mode. The supervisor's optional stdin and scrubbed streaming observer leave command-step behavior unchanged.
39. **Compatibility evidence is distinguished from live verification.** Codex passes the shared conformance suite through a synthetic CLI fixture, so its registry entry is `conformance_passed`. Installed help markers verify required features, but authentication/provider stream framing/resume remain unverified. Missing resume capability disables correction instead of launching fresh. Per-invocation env policy and disabled shell snapshots support report-token delivery without global config edits; exact argv, inherited environment and remaining live checks are recorded in `docs/harness-compatibility.md`. Milestone 0.5 and the full Phase 6 gate remain open.


## Pi adapter decisions (phase 6.2)

40. **Pi uses one-shot JSON and runner-owned sessions.** The installed package is `@earendil-works/pi-coding-agent` 1.3.0. LF-only UTF-8 framing is bounded to 1 MiB per record; CRLF is accepted and a final unterminated record is a protocol failure. `agent_end` can precede retries; only a final non-aborted `agent_settled` plus process/group/pipe settlement permits success. Transient failed assistant messages can recover within Pi; final provider failures, aborts, truncation and malformed streams bypass report correction. Stdout has no report authority. No workflow field, migration or correction/routing rule changes.
41. **Resume is exact and cannot create a session.** Fresh sessions have dedicated directories under `pi-sessions` beside logs or explicit adapter `sessionDir`. A streamed UUID must match a persisted v3 header before the absolute file path is eligible for durable session identity. Resume validates file/header/UUID/cwd and uses the full UUID with its exact directory. This avoids Pi's missing-path and `--session-id` create-if-missing behavior; no recent-session/selector/fork flags or fresh fallback. Model/thinking use existing parameters; unsupported thinking levels fail before launch. Normal unrestricted Pi tools use no permission flag. Offline probes isolate Pi config/resources; provider environment selection, version evidence and live limitations are recorded in `harness-compatibility.md`. Pi's shared offline conformance supports registry status only; 0.5 and the full Phase 6 live gate stay open.


## Claude Code adapter decisions (phase 6.3)

42. **Claude uses the existing reporting and session contracts.** The async factory probes offline with temporary home/config and no provider credentials. Print mode uses stdin and bounded LF stream-json; only a successful final `result` plus confirmed process/group/pipe settlement permits clean completion. Provider/protocol failures bypass correction, including on exit zero. Native retry progress may recover before the terminal result. Stdout never supplies reports.
43. **Persistent exact UUID resume and unrestricted permissions.** Default CLI persistence stays enabled; terminal identity must match init and any requested UUID. Resume uses only `--resume <full-UUID>` without selectors, fork, ephemeral mode or fresh fallback. Installed missing-UUID evidence confirms explicit failure. Existing model/reasoning fields use `--model` / validated `--effort`; invocation events audit version and `bypassPermissions`. A deliberate Claude/Anthropic environment and common secret scrubbing preserve report access. Full shared synthetic offline conformance supports `conformance_passed`, not authenticated/live compatibility. No schema fields, migrations, correction rules or new approval gates were added; exact evidence and remaining checks are in `harness-compatibility.md`.

## OpenCode adapter decisions (phase 6.4)

44. **Exact v2 API resume instead of CLI create-or-continue.** Installed OpenCode v2.0.32 confirms that `run --session` creates absent sessions. The adapter therefore uses an invocation-local private `serve --stdio` child and exact API prompt admission, never a session-create request during resume. Identity/cwd, generated prompt acknowledgment, explicit wait and a fresh persisted terminal outcome are validated. A required missing API identity is a protocol failure, not a clean missing-report execution. Only success plus common process/group/pipe settlement permits report routing/correction; no YAML fields, migrations or runner policy changes are needed.
45. **Private ownership and explicit unrestricted rules.** The bridge holds the server stdin lease, then closes it and awaits exit under common supervision; it does not manage the shared OpenCode service. A random invocation-local Basic-auth password is not persisted or logged. Session permission rules explicitly allow all actions/resources and are audited as `session-allow-all`; they override denials for that session rather than using CLI `--auto`. `model` accepts provider/model#variant; `reasoning_effort` requires an explicit provider/model without a variant and supplies that named variant. The minimal API path exposes no provider event stream. Full synthetic offline conformance is not live verification; exact evidence/environment selection is in `harness-compatibility.md`.

## omp adapter decisions (phase 6.5)

46. **omp is a verified Pi-family dialect, not Pi protocol parity.** The shared process/report adapter launches stdin print JSON as identity `omp`, with fatal UTF-8/LF framing, explicit terminal `agent_end.isTerminal: true`, final assistant evidence and common process/group/pipe settlement. There is no Pi `agent_settled` in omp. Native retries and `auto_compaction_*` may recover; terminal/provider/protocol failures bypass correction. Existing model/reasoning fields map to `--model` / `--thinking`, including `auto`. `--approval-mode yolo` and version are audited; explicit tool/user restrictions and provider safety checks remain effective.
47. **omp resumes strict full paths, not Pi's UUID lookup.** Dedicated persistent directories and matching v3 UUID/header/cwd establish an absolute journal identity, accepting omp's physical title slot. Exact path resume uses the installed strict non-creating open branch; prefix/global/latest lookup, restore and forks are not used. Missing/mismatched/moved-away or malformed/truncated/oversized-record journals are unavailable rather than fresh fallback. Full shared synthetic conformance and an installed deletion-after-precheck negative smoke support `conformance_passed`, not live authentication/provider/tool verification. No workflow fields, migrations, report bounds, session scope or correction policy change; exact commands and installed fresh-database limitations are in the implementation log and compatibility note.


## Capability preflight decisions (phase 6.6)

48. **One offline probe convention, two validation stages.** Inventory now uses the same adapter factories as execution, replacing the separate help-marker table. Required probes fail closed on failed/truncated evidence; optional model/reasoning/resume features are gated individually. `supportsReasoningEffort` is capability metadata for an existing YAML field, not a new workflow option. Effective snapshots reflect implemented transport: no structured stdout report fallback; OpenCode has no provider event stream. Callers recreate adapters after changing a CLI.
49. **Preflight errors use existing outcomes.** The runner checks selected capabilities immediately before each effective attempt, including task/revision settings. Unsupported model/reasoning selection uses `system.spawn_error`; unsupported explicit resume uses `system.resume_unavailable`. Known adapter-authored option/session errors retain safe explanations, while arbitrary exceptions remain generic. Missing optional correction support preserves fresh execution and existing clean missing-report policy. Per-session availability and exact non-creating admission remain adapter-owned. Coordinator transactions, report tokens/correction bounds, migrations and YAML fields are unchanged; live-provider checks stay separate.
