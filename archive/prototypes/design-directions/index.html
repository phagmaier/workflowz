Workflowz: three design directions

Each prototype shows the same workflow (Implement, review and commit on a sample tiny-ledger project) and the same paused run. All four views — Workflows, Create/Edit workflow, Runs and Run details — are clickable, and browser back/forward works. Use Prototype controls (bottom right) to switch the run between ready, running, pausing, paused, interrupted, stopped and completed, or to simulate a stale run or a lost daemon connection.

A

Developer workspace

Sidebar navigation and breadcrumbs. A three-pane editor (steps · selected step · checks) with Steps / Project / Rules & limits / YAML tabs. The run page shows a decision bar, then the history next to step details.

Good at

  • Speed for repeat use; everything is one click away
  • Scales to long workflows and long runs
  • Feels like tools you already use (GitHub, Linear)

Costs

  • Most on screen at once; tabs must be learned
  • Branching is read from dropdowns, not seen

B

Guided builder

Top navigation and a single reading column. The editor walks through Basics → Steps → Safety → Review & save. Steps are cards summarised in sentences. The run page asks “What should happen next?” and tells the story task by task.

Good at

  • Least jargon; consequences explained where you choose
  • Save → Create run → Start is an obvious sequence
  • Paused-run decisions are explicit choices

Costs

  • More scrolling and clicks for experienced use
  • Weak overview of loops and branches
Open editor Run details Start at Workflows
C

Visual workflow studio

Icon rail, toolbar and an auto-arranged map of steps. You edit the selected step in an inspector. A bottom drawer holds Problems, Project, Rules and YAML. The run page draws the path taken on the same map, with a timeline and raw events.

Good at

  • Loops, branches and missing destinations are visible at a glance
  • The run map shows which path ran and how often

Costs

  • Most expensive to build and make accessible
  • Dense IDE feel; weakest on small screens
  • The map gets busy as outcomes grow

Same in all three (existing contracts)

  • Save creates a new immutable revision; earlier revisions and runs don’t change.
  • Create run copies tasks and prepares a ready run. Start is a separate, explicit action.
  • Pause waits for the current step to finish. Stop ends the owned process, waits for it to exit and needs a reason. Resume needs a reason.
  • Jump, skip-with-result and mark-task-done need a reason and leave the run paused.
  • Editing a paused run’s workflow affects only future steps and needs a reason.
  • Interrupted runs point to the existing CLI recovery. The browser has no recovery API, and none is added here.
  • Stale-state rejections and disconnects are reported at the action that failed and are never retried automatically.
  • Unrestricted harness permissions are stated where agents are chosen and before Start.

Not prototyped yet

  • Editing YAML as text (each direction shows only the entry point)
  • Creating shared rules (policies): existing rules display, and the add button is a stub
  • The pairing screen and empty/loading states for every list
  • Validation is an illustrative stand-in. The real compiler stays the authority.
